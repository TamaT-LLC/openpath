# 非機能テストの計測結果: openpath

TST-001 §5 の非機能テストを `scripts/measure-*.sh` で計測した手順と結果を記録する（Issue #30）。対象の要件は REQ-001 の NFR-01（通信ゼロ）、NFR-03（アイドル CPU 0.1% 未満・常駐メモリ 50MB 以下）、NFR-04（Notarization）と FR-DETECT-03（検知からパレット表示まで 300ms 以下）。

主な結果は macOS 27.0 での計測（§2）で、macOS 26.3.1 で測った値は §5 に比較として残す。

## 1. 結果の要約

| 項目 | 合格基準 | 結果（2026-09-24、macOS 27.0） | 判定 |
| --- | --- | --- | --- |

計測用インスタンスは、一時ディレクトリ（`$TMPDIR/openpath-measure-TASK-030.XXXXXX`）の `home/` を一時 HOME にして、次のように起動する。

```bash
open -n -g --env CFFIXED_USER_HOME=<一時 HOME> build/openpath.app --args -onboardingFinished YES -enabled YES
```

- 設定・履歴・ログはすべて一時 HOME 配下にでき、実ユーザーの `~/.config/openpath`・`~/Library/Application Support/openpath`・`~/Library/Logs/openpath` には触れない。計測の前後で実ユーザーの `~/Library/Preferences/jp.tamat.openpath.plist` の更新時刻とサイズが変わらないこと、一時 HOME 配下に `Library/Preferences` ができないこと（アプリが UserDefaults に書き込まないこと）も確かめた
- `-onboardingFinished YES -enabled YES` は UserDefaults の引数ドメインで、保存はされない。初回起動の案内（#67。アプリを前面に出すウインドウ）を出さず、メニューの「有効」の記録（#69）にかかわらず有効の状態で、常用時と同じ状態を測る。起動ログの「有効: はい」で効いていることを確かめた

- `include_files = false`、`depth = 2`、ghq は無効
- アクセシビリティ権限は無い。そのためパネルの検知（PanelWatcher の 200ms ポーリング）は動かない

## 3. 手順と結果

計測スクリプトの終了コードは 0 = PASS、1 = FAIL、2 = 計測できなかった（対象のプロセスやログが無い等）。計測用インスタンスを止めるときは `measure-isolated.sh stop` を使い、start で起動した pid だけを止める（`pkill` / `killall` は使わない）。

| スクリプト | 役割 |
| --- | --- |
| `scripts/measure-isolated.sh` | 計測用インスタンスの起動（`start [--candidates N] [--settle-seconds S]`）と停止（`stop <計測ディレクトリ>`）。start は累積 CPU 時間の増分が 5 秒間 0.02 秒以下になるまで（候補の構築が落ち着くまで）待ち、`OPENPATH_PID` 等を KEY=VALUE で出力する |
| `scripts/measure-memory.sh` | phys_footprint の現在値で常駐メモリを判定する。ピークと RSS は参考値 |
| `scripts/measure-idle-cpu.sh` | 累積 CPU 時間の増分 ÷ 経過実時間でアイドル時の平均 CPU% を出す。`top` の %CPU を参考値として併記する |
| `scripts/measure-network.sh` | `nettop` の送受信バイト数と `lsof -i` のインターネットソケット数を監視する |
| `scripts/measure-detection-latency.sh` | ログの `panel detected` → `palette shown` のタイムスタンプ差から p50 / p95 / 最大を出す。パネルの ID で組にする |

### 3.1 メモリ（NFR-03）

候補の構築が落ち着いてから 30 秒後に測る。測るタイミングで値が変わるため、起動・構築完了からの経過時間を揃えて 5 回起動し直して測った。

```bash
eval "$(scripts/measure-isolated.sh start --candidates 20000)"
sleep 30
scripts/measure-memory.sh --pid "$OPENPATH_PID"
scripts/measure-isolated.sh stop "$OPENPATH_MEASURE_DIR"
```

1 回だけ測るなら `scripts/measure-memory.sh --candidates 20000` でもよい（起動から停止までを行い、落ち着いた直後に測る）。

候補 20,000 件、落ち着いてから 30 秒後（`footprint` で取得。1 MB = 1,048,576 バイト）:

| 回 | 計測時刻 | phys_footprint 現在値 | ピーク（起動後の最大） | RSS（参考） | 判定 |
| --- | --- | --- | --- | --- | --- |
| 1 | 15:30:10 | 39.92 MB | 50.70 MB | 95.02 MB | PASS |
| 2 | 15:40:57 | 40.08 MB | 50.50 MB | 97.52 MB | PASS |
| 3 | 15:41:37 | 41.06 MB | 50.49 MB | 75.75 MB | PASS |
| 4 | 15:42:18 | 40.53 MB | 50.58 MB | 50.05 MB | PASS |
| 5 | 15:43:00 | 39.95 MB | 50.27 MB | 87.12 MB | PASS |

現在値の中央値は 40.08 MB、最大は 41.06 MB（基準まで 8.94 MB）。起動時の構築中のピークは 5 回とも 50 MB を少し超えた（50.27〜50.70 MB）。

周期の再構築（構築完了から 5 分ごと）を経た後と、候補数を変えたときの値（参考）:

| 状況 | phys_footprint 現在値 | ピーク（起動後の最大） |
| --- | --- | --- |
| 候補 20,000 件、再構築 1 回の 85 秒後（通信の計測に使ったインスタンス） | 44.45 MB | 67.28 MB |
| 候補 20,000 件、再構築 2 回目の 33 秒後（アイドル CPU の計測に使ったインスタンス） | **57.64 MB** | 59.72 MB |
| 候補 5,000 件、落ち着いてから 30 秒後 → 再構築 2 回目の 43 秒後 | 26.30 MB → 32.13 MB | 28.03 MB → 32.16 MB |
| 候補 0 件（2 回） | 20.30 MB / 20.20 MB | 20.78 MB / 20.94 MB |

再構築の後にメモリが戻るのか、再構築のたびに積み上がるのかを見るため、候補 20,000 件のインスタンスで phys_footprint を 15 秒ごとに 16 分（再構築 3 回分）記録した（main 95089e4 の .app）。

| 区間（再構築の時刻はログの上限到達の警告） | 時刻 | phys_footprint 現在値 |
| --- | --- | --- |
| 構築が落ち着いた後、再構築の前 | 15:57:26〜16:02:14 | 39.22〜39.89 MB（起動時の構築中のピーク 51.11 MB） |
| 再構築 1 回目（16:02:26.8） | 16:02:29 | **56.67 MB** → 15 秒後に 39.95 MB |
| 再構築の間 | 16:02:44〜16:07:16 | 39.89〜40.00 MB |
| 再構築 2 回目（16:07:29.3） | 16:07:31〜16:09:31 | **59.53〜59.59 MB が約 2 分続く** → 16:09:46 に 50.17 MB → 16:10:01 に 45.72 MB → 16:10:17 に 42.38 MB |
| 再構築の間 | 16:10:17〜16:12:17 | 42.34〜42.41 MB |
| 再構築 3 回目（16:12:30.6） | 16:12:32〜16:12:47 | **61.42 / 61.38 MB** → 16:13:02 に 48.09 MB → 16:13:17 に 40.89 MB |

64 サンプルのうち 13（約 2 割）が 50 MB を超え、起動後の最大は 61.44 MB。再構築のたびに積み上がることはなく、再構築の後は 40〜42 MB に戻る。再構築の直後の増分（約 17〜22 MB）は、旧い候補をインデックスに残したまま新しい候補を作る分と考えられる。戻るまでの時間が 15 秒〜約 2 分 15 秒とばらつくのは、解放したメモリをアロケーターが OS に返す時機によると考えられる（推定。調べていない）。前記の「再構築 2 回目の 33 秒後で 57.64 MB」も、この戻る前の値にあたる。

### 3.2 アイドル CPU（NFR-03）

```bash
eval "$(scripts/measure-isolated.sh start --candidates 20000)"
sleep 30
scripts/measure-idle-cpu.sh --pid "$OPENPATH_PID"   # 既定 10 分、top は 5 秒間隔
scripts/measure-isolated.sh stop "$OPENPATH_MEASURE_DIR"
```

候補数への依存を見るため、候補 5,000 件（DSN-002 §8 の roots 走査の目標と同じ件数）でも同じ手順で測った。

| 候補数 | 計測期間（経過実時間） | 累積 CPU 時間の増分 | 平均 CPU% | `top` の %CPU（参考） | 判定 |
| --- | --- | --- | --- | --- | --- |
| 20,000 件 | 15:30:11〜15:40:17（606 秒） | 1.16 秒 | **0.1914%** | 119 サンプル、平均 0.180% / 最大 9.2% | **FAIL** |
| 5,000 件 | 15:44:52〜15:55:03（611 秒） | 0.37 秒 | 0.0606% | 119 サンプル、平均 0.050% / 最大 2.3% | PASS |

平均 CPU% の分解能（増分 0.01 秒あたり）はどちらも約 0.0016%。経過実時間が 10 分より少し長いのは `top` の 1 サンプルあたりの所要時間の分で、平均は実際の経過実時間で割っている。

計測中に累積 CPU 時間を 5 秒ごとに記録した（`ps -o time`。読み取りは対象の CPU 時間を消費しない）ところ、増分の大半は構築完了から 5 分ごとの周期の再構築（`CandidateIndexRebuilder.defaultInterval`）だった。

| 候補数 | 周期の再構築 1 回あたりの CPU 時間 | 再構築以外（窓全体に対する平均） |
| --- | --- | --- |
| 20,000 件 | 約 0.47 秒（15:34:35）、約 0.54 秒（15:39:44）。いずれもログの上限到達の警告と同時刻 | 約 0.15 秒（約 0.02%）。0.01〜0.02 秒の増分が数十秒おき |
| 5,000 件 | 約 0.12 秒（15:49:19）、約 0.12 秒（15:54:20） | 約 0.13 秒（約 0.02%） |

再構築を除けばアイドル時の CPU は 0.02% 前後で基準を大きく下回るが、候補 20,000 件では 5 分ごとに約 0.5 秒（5 分あたり約 0.17%）を再構築に使うため、平均が 0.1% を超える。再構築のコストが候補数に比例すると仮定すると（5,000 件で約 0.12 秒と、ほぼ比例している）、9,000 件前後が境目になる（推定。計測はしていない）。

### 3.3 ネットワーク（NFR-01）

起動直後から監視するため、`--settle-seconds 0` で起動を待たずに監視を始める。監視期間には起動時の候補の構築と、その 5 分後の周期の再構築を含める。

```bash
eval "$(scripts/measure-isolated.sh start --candidates 20000 --settle-seconds 0)"
scripts/measure-network.sh --pid "$OPENPATH_PID" --seconds 390
scripts/measure-isolated.sh stop "$OPENPATH_MEASURE_DIR"
```

| 項目 | 値 |
| --- | --- |
| 監視期間 | 15:23:00〜15:29:30（390 秒）。起動は 15:23:00.266、起動時の構築は 15:23:01.455 に上限に到達、周期の再構築は 15:28:06 に上限に到達（いずれも監視期間内） |

| `lsof -i` | 79 回。インターネットソケット（IPv4 / IPv6、loopback を含む）最大 0 個 |
| 判定 | PASS |

### 3.4 検知レイテンシ（FR-DETECT-03）: 計測できず

PR #69 で、パレットを表示するたびに `palette shown (id: open-panel-N)` が info で出るようになった（`panel detected (id: open-panel-N, …)` と同じ書式・同じパネル ID）。しかしこの環境ではアクセシビリティ権限を付けられず、PanelWatcher が動かないため `panel detected` がログに出ない。手順は §6.1。

`measure-detection-latency.sh` はパネルの ID で組にする。始点の `panel detected` は PanelWatcher がパネルを検知した直後に出るため、測れるのは検知からパレット表示まで（FR-DETECT-03 の定義どおり）で、パネルが生成されてから検知されるまで（AX 通知の遅れや 200ms ポーリングの待ち）の時間は含まれない。

- `palette shown` に ID があれば、同じ ID のまだ組んでいない `panel detected` と組にする。間に別のパネルの検知が挟まってもよい
- ID の無い終点（`--end-pattern` で別の行を指定したとき）は、直前の始点がまだ組んでいなければそれと組にする
- `panel gone` と起動の行（`を起動します`）で、まだ組んでいない始点をすべて打ち切る。ID はプロセスごとの連番で、再起動すると同じ値が使われるため
- 同じパネルの再表示・ホットキーでの再表示で出る、組む相手の無い `palette shown` は件数だけ数える

合成ログで次を確かめた（期待値は手計算、15 ケース）。

- 実アプリの書式で 20 組の差から p50 / p95 / 最大を nearest-rank 法で出し、閾値ちょうどは PASS、超えると FAIL。各パネルでの再表示（組む相手の無い `palette shown`）は件数だけ数える
- 別のパネルの検知が間に挟まっても ID が同じもの同士で組む。再起動で同じ ID が再利用されても前の起動の検知とは組まない。同じ ID の検知が続いたら新しい方と組む
- 秒・分・日・月末・閏日・年をまたぐ差、`+09:00` / `-05:00` / `Z` / `+0900` のオフセット、小数 1 桁のミリ秒
- ID の無い終点、`panel gone` の後の終点、end が start より前の組、解釈できないタイムスタンプを除外して件数を報告する
- ローテーションされた `openpath.log.1` と `openpath.log` をこの順に続けて読む（既定のログの探索も含む）
- ログが無い・`palette shown` が 1 行も無い（PR #69 より前のビルド）・`panel detected` が 1 行も無い・1 組も組めないときは終了コード 2

## 4. 注意点

- **メモリの余裕が小さい**: 候補 20,000 件の落ち着いた後の現在値は 39〜42 MB で、基準の 50 MB まで 8〜11 MB しかない。起動時の構築中のピークは 50.27〜51.11 MB、周期の再構築の直後は 56.67〜61.42 MB と、どちらも 50 MB を超える。常駐メモリを「落ち着いた後の値」と読むなら PASS だが、「再構築の後も含めて常に 50 MB 以下」と読むなら FAIL であり、どちらで判定するかはオーナーの判断が要る（§6.4）。候補 0 件（約 20 MB）との差は約 20 MB で、DSN-002 §8 の `CandidateIndex` が保持する分（8.6 MB、PR #57）より大きい。残りの内訳（走査や前処理の一時領域がプロセスに残る分等）は調べていない。候補数はルートあたり 20,000 件が上限だが、ルートを複数置く・`include_files = true` にすると候補はさらに増える。
- **メモリは測る時点で大きく変わる**: 再構築の直後は、戻るまでの 15 秒〜約 2 分 15 秒のあいだ 50 MB を超えたままのことがある。1 回だけ測ると、再構築からの経過時間によって 40 MB 前後にも 60 MB 前後にもなるため、構築が落ち着いてから一定時間（本書では 30 秒）後に揃えて測り、再構築の影響は時系列で別に見る。
- **RSS ではなく phys_footprint で判定する**: phys_footprint は Activity Monitor の「メモリ」列・`footprint` コマンドと同じ値で、プロセスが専有するメモリ（圧縮・スワップされた分を含む）を表す。RSS は共有フレームワークのページを含む一方、圧縮・スワップされたページを含まないため、phys_footprint より大きくも小さくもなる。今回も、同じ条件の 5 回で phys_footprint が 39.92〜41.06 MB に収まったのに対し、RSS は 50.05〜97.52 MB とばらついた（macOS 26.3.1 では、候補 0 件で phys_footprint 16.00 MB に対し RSS 31.55 MB、再構築の後で phys_footprint 35.44 MB に対し RSS 20.16 MB と、どちらの向きにもずれた）。`footprint` が task port を取れないときは `top -stats mem`（K / M 単位に丸められ、ピークは取れない）で代わりに取り、どちらを使ったかを出力に書く。
- **nettop は起動直後から回す**: `nettop` の値は、動かし始めてから観測したフロー（途中で閉じたものを含む）の累積で、監視を始める前に閉じたフローは数えられない。そのため `measure-isolated.sh start --settle-seconds 0` の直後に `measure-network.sh` を実行する。それでも起動からログファイルができるまで（1 秒未満）は監視の外になる。ソケットを持たないプロセスは `nettop` の出力に行が出ないため 0 バイトとして扱い、プロセスが動き続けていることは別に確かめる。
- **権限なしで測っている**: 計測用インスタンスにはアクセシビリティ権限が無いため、パネルの検知の 200ms ポーリングはアイドル CPU に含まれていない。権限付きでの計測はオーナーが行う（§6.2）。
- **アイドル CPU は 5 分ごとの周期の再構築を含めて測る**: 再構築の CPU 時間はアイドル時の平均の大半を占めるため、再構築を含まない短い計測（例: 30 秒）では過小評価になる。10 分（再構築 2 回分）以上測る。また、候補数によって合否が変わるため、計測時の候補数を必ず記録する。
- **計測中は操作しない**: パレットを開く・ホットキーを押す等の操作は計測値に入る。計測用インスタンスはホットキー（ctrl+shift+o）も登録するため、計測中は押さない。
- **macOS のバージョンで値が変わる**: 同じマシン・同じ方法で、macOS 26.3.1 から 27.0 に上がるとメモリは候補 0 件で約 4 MB、候補 20,000 件の落ち着いた後で約 4 MB 増え、起動時のピークは 50 MB を超えるようになった（§5）。この間にアプリのコードも #67・#69 の分だけ変わっているため、どちらの寄与かは切り分けていない。記録には macOS のバージョンを必ず残す。

### 6.4 アイドル CPU の FAIL とメモリの扱いを決める

TST-001 §6 の完了条件（5 章の合格基準を満たす）に対し、候補 20,000 件のアイドル CPU は基準を満たさない。また、常駐メモリは落ち着いた後は 40〜42 MB だが、周期の再構築の後は 15 秒〜約 2 分 15 秒のあいだ 50 MB を超える（最大 61.44 MB、macOS 27.0）。次のどれで扱うかの判断が要る。

- 合格基準の条件を明確にする（例: アイドル CPU は候補数を定めて測る、常駐メモリをどの時点の値で判定するか）
- アプリ側で周期の再構築のコストを下げる（例: ルートの変更が無ければ走査を省く、FSEvents で変更を検知する、周期を延ばす）。アイドル CPU と再構築の直後のメモリの両方に効く。いずれも `Sources/` の変更で、本 PR の範囲外
- 現状を既知の制約として受け入れ、REQ-001 NFR-03 の「目標」の扱いを記録する
